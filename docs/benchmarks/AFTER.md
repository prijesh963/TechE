# Context Measurement — After Snapshot

Captured after architecture items #1-#4 landed (symbol/dependency graph,
hybrid retrieval, query/intent classification, graph-grounded citations —
see `docs/CODEBASE_INTELLIGENCE_DESIGN.md`). Generated by
`scripts/context-measure-samples.mjs`, which reuses the new
`ContextMeasurementService` (`packages/measurement`, item #5) and diffs
against `docs/benchmarks/baseline-context-snapshot.json`. Raw data in
`after-context-snapshot.json`.

## Method

Same canonical request as the baseline (`"Add invoice approval workflow"`),
but with one deliberate methodology change: "naive whole repo" is now
measured via `scanRepository`/`isBinaryPath` (`@copilot-architect/shared`)
— the same exclusion/binary logic `packages/indexer` itself uses — instead
of the original script's hardcoded source-extension allowlist. This is a
more accurate "everything the tool would consider readable source" naive
baseline, but it means **the naive file counts below are not the same
measurement as the baseline's**, so the `reduction %` column isn't a clean
before/after diff by itself. The `Selected tokens` column (unaffected by
the naive-definition change — it only counts `plan.relevantFiles`) is the
real apples-to-apples comparison.

Before each sample was measured, `graph` was run against it first (same as
a real user would before `plan`), so items #1/#2/#4 (graph-signal ranking,
graph-grounded citations) get a fair chance to contribute.

## Honest read

**The `reduction %` column improving is misleading on its own** — it's an
artifact of the naive-definition change (see Method), not evidence that
items #1-#4 select less content. Looking at the column that _is_
apples-to-apples, **selected tokens went up in every single sample**, by
one to two extra files each. `polyglot-monorepo` (previously the standout
at 85.6% reduction, `relevantFileCount: 1`) now selects 3 files and its
reduction percentage actually _drops_ slightly (82% vs 85.6%) despite the
larger naive denominator working in its favor.

This is a real, reportable finding, not a measurement bug: hybrid
retrieval's multi-signal fusion (lexical + structural + graph + recency)
is designed to broaden candidate discovery — #2's own design doc says so
explicitly ("graph signal surfaces files that don't share vocabulary").
On these tiny fixture repos (3-12 files), that broadening has no
irrelevant content left to filter out in exchange, so the net effect is
strictly more files selected, not fewer. The `samples/` fixtures were
built for fast unit tests, not to exercise "does hybrid retrieval actually
narrow context on a real repo" — see `BASELINE.md`'s own caveat that most
of them already returned "every file in the repo" before any of this work
started.

**On a repo large enough to have room to filter, the picture is
different.** Running the same request (`"Add invoice approval workflow"`)
against this repo's own codebase (243 non-binary source files, not a
`samples/` fixture) selects 8 files at ~86% estimated token reduction —
the selection is small and sensible relative to the whole repo, citing
real entity matches, recency, and (for `packages/planner/src/models.ts`)
graph-adjacent recency signals. There's no "before" snapshot for this repo
(it didn't exist pre-#1 in a comparable form), so this isn't a diff — it's
a standalone data point showing where the tooling's value actually shows
up: real repos with enough files that "relevant" is a meaningfully small
fraction of "everything," not 3-12 file fixtures where it usually isn't.

## Takeaway

Item #5 did its job: it replaced an assumption ("this should reduce
context") with a measurement, and the measurement's honest answer is
mixed. On tiny repos, items #1-#4 do not reduce absolute selected content
— if anything they select a bit more, because broader signal fusion finds
additional weakly-related files with nothing to trade off against. On a
real, larger repo, the reduction is substantial. Any future work claiming
a token-reduction improvement should be checked against
`ContextMeasurementService`/`measure` — and ideally against a repo with
enough files for the claim to be testable — rather than assumed.

## Re-running

```bash
npm run build
node scripts/context-measure-samples.mjs
```

This overwrites `after-context-snapshot.json`. For a single arbitrary repo
and request (not the sample matrix), use the harness directly:

```bash
npm run cli -- measure "your feature request" --path <repo> --json
```
