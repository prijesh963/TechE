# Context Baseline — Before Snapshot

Captured 2026-09-14, before architecture item #1 (symbol/dependency graph)
and everything downstream of it (see
`docs/CODEBASE_INTELLIGENCE_DESIGN.md`). Generated by
`scripts/context-baseline.mjs`; raw data in `baseline-context-snapshot.json`.

## Method

For each repo under `samples/`, run `FeaturePlanningService.
createPlanPreview()` (read-only — writes nothing to the sample repos) with
the canonical request `"Add invoice approval workflow"`, then compare:

- **naive**: byte size of every source file in the repo (as if the whole
  repo were sent as context)
- **current tool selection**: byte size of only the files
  `plan.relevantFiles` points to

Token counts are a rough chars ÷ 4 estimate — directional only, not a real
tokenizer and not a GitHub Copilot billing measurement (see the caveat in
`docs/CODEBASE_INTELLIGENCE_DESIGN.md` about the difference between the
two).

## Honest read

The `samples/` fixtures are intentionally tiny (3–6 files each, built for
fast unit tests), so most of them show little to no reduction — the
current keyword-scored selection often just returns "every file in the
repo" because there's nothing to filter out. That's expected and not a
finding in itself; the point of this snapshot isn't to claim a win today,
it's to lock in a repeatable measurement on repos we'll re-measure later.

`polyglot-monorepo` (85.6%) and the Java samples (~18%) are the only
samples where the file count is large enough relative to the request for
the selection to actually narrow anything — those are the ones worth
watching for regression or improvement once the symbol/dependency graph
(#1), hybrid retrieval (#2), and graph-based citations (#4) land.

## Re-running

```bash
npm run build
node scripts/context-baseline.mjs
```

This overwrites `baseline-context-snapshot.json` with a new "current"
snapshot — diff it against a checked-out copy of this file to see the
before/after once the downstream work lands, rather than losing the
comparison point.
